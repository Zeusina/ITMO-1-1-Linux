## Часть 3

Права устроены следующим образом, их можно разбить на тройки бит, каждый бит отвечает за определенное право. 
SUID/SGID/sticky bit|rwx(user)|rwx(group)|rwx(others)
Они преобразуются в цифры внутри троек, через обычное преобразование в десятичную систему, то есть права r-x(101) становятся 4*1 + 2*0 + 1*1 = 5

Так как по ТЗ подразумевается, что любой пользователь может создавать файлы в этой директории, но удалять и переименовывать может только свои файлы, права доступа я установил `3777`. Благодаря SGID создаваемые файлы наследуют группу-владельца `project`, а благодаря sticky bit пользователи не могут удалять и переименовывать чужие файлы. При этом пользователи группы `project` могут изменять содержимое чужих файлов, если на самих файлах установлены соответствующие права. Права создаваемых файлов зависят от `umask` пользователя (`umask` убирает определенные биты из запрошенных при создании файла прав, из-за чего они становятся более строгими). При таком значении ядро ограничивает открытие чужих файлов с флагом `O_CREAT` в директориях со sticky bit, доступных для записи группе или всем пользователям. При проверке, если создать файл пользователем `u1`, то `u3` не сможет его удалить или переименовать из-за sticky bit, а также не сможет открыть его для записи через перенаправление вывода из-за `fs.protected_regular`. При этом открытие существующего файла для записи без флага `O_CREAT` при наличии соответствующих прав остается возможным.

## Вопросы и задания

1. Задание парольной фразы защищает от утечки ключа, то есть если приватный ключ будет скомпрометирован им будет нельзя воспользоваться, не зная пароля.

2. Так как в `ssh` нет центрального механизма доверия (без использования SSH CA) необходимо при первом подключении к серверу удостовериться что это действительно он, а не ловушка, например для атаки MITM. Поэтому нужно при первом подключении подтвердить публичный ключ сервера. Если он изменился SSH покажет явное предупреждение, его изменение может означать, как например то, что по текущему адресу расположен новый сервер, так и то, что кто-то пытается перехватить SSH сессию.

3. При одинаковых паролях нельзя это определить, так как они хранятся в хешированном виде и хешируется не только сам пароль, вместе с ним хешируется случайная соль и из-за этого одинаковые пароли дают разные хеши.

4. Таблица

| Атрибут      | Название | Для файла                   | Для каталога                                                    |
| ------------ | -------- | --------------------------- | --------------------------------------------------------------- |
| `r`          | Read     | Чтение                      | Просмотр содержимого                                            |
| `w`          | Write    | Изменение                   | Создание и удаление файлов (также нужен `x`)                    |
| `x`          | Execute  | Выполнение                  | Доступ к элементам                                              |
| `suid`       | Set UID  | Выполнение с EUID владельца | Обычно не действует                                             |
| `sgid`       | Set GID  | Выполнение с EGID группы    | Наследование группы                                             |
| `sticky bit` | Sticky   | Обычно не действует         | Удаление только владельцем (также владельцем каталога и `root`) |

5. Для каталога `x` означает не право выполнения а право доступа к элементам, поэтому для манипуляций со списком файлов (модификации/получения атрибутов) необходим `x`, поэтому читать можно при `r`, а для создания файлов и нужен `wx`. Sticky bit на каталог изменяет поведение таким образом, что в нем могут создавать файлы все, кто имеют на это право, но переименовывать и удалять можно только свои файлы.

6. Команда будет следующей

```bash
sudo setfacl -m u:user:rwx /путь/к/файлу
```

7. `su`, `su –` и `sudo` отличаются работой с окружением, первые две команды переключают пользователя с разной степенью изоляции от исходного окружения, `sudo` же имеет высокую и гибкую изоляцию от исходного окружения пользователя, а также все действия пользователей журналируются с указанием вызвавшего пользователя, при этом он не требует пароль `root`, что важно для безопасности, потому что чем реже он используется тем меньше возможностей его захватить и атаковать сервер.

8. Ограничение удалось обойти через команду `sudo passwd -d root`. Так как у меня в whitelist указана команда `passwd` без аргументов, а в blacklist с аргументом `root` если поставить между `passwd` и `root` что-то, то `sudo` пропустит такую команду. Мое правило можно доработать через регулярные выражения, чтобы разрешать ровно один аргумент к `passwd`. Правила c подстановочными знаками опасны, так как можно передать неразрешенные параметры в разрешенную команду и вызвать неожиданное поаведение.

9. `SIGTERM` это сигнал который дает процессу корректно завершиться и дает себя перехватить, процесс может на него даже не реагировать, `SIGKILL` же принудительно завершает процесс и освобождает его ресурсы без корректного завершения.

10. Процесс с `&` при отключении сессии должен завершится, потому что оболочка отправит ему `SIGHUP`, но в моем случае оболочка по умолчанию не отправляет `SIGHUP` (параметр `huponexit` выключен) при завершении, поэтому процесс продолжает работу, `nohup` заставляет процесс игнорировать `SIGHUP`, поэтому даже если ему отправят этот сигнал, он не завершится и продолжит работу. В обоих моих случаях процесс станет сиротой и его усыновит `init`.

11. Зомби процесс – процесс, завершивший выполнение, но его родитель еще не считал его код завершения, он больше не выполняет код и не занимает оперативную память, но занимает PID. Завершить его через `kill -9` нельзя, так как он уже завершен и не обрабатывает сигналы.

12. `sshd -T` показывает актуальную рабочую конфигурацию `sshd`, она может отличаться от файлов на диске если например параметр закомментирован, но он имеет значение по умолчанию. Формально он не задан, но в активной конфигурации он присутствует(параметр Port по умолчанию закомментирован и имеет значение 22).

13. Если у исполняемого файла владелец `root` и у него установлен `suid`, возникает риск того, что если пользователь имеющий к нему доступ найдет в нем уязвимость позволяющую выполнять код, он будет выполняться с правами `root`.
